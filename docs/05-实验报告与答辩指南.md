# 5. 实验报告与答辩指南

## 5.1 你上台时要讲清楚的主线

不要从安装软件开始讲。最清楚的逻辑是：

```text
为什么选 OpenRichpedia
→ 原始数据有什么结构
→ 我怎样把它抽象成节点和关系
→ 为什么需要清洗和统一 ID
→ 怎样导入 Neo4j
→ 用 Cypher 查到了什么
→ 图数据库为什么适合知识图谱
```

## 5.2 30 秒项目介绍

可以按自己的语言讲：

> 我选择的是 OpenKG 上的 OpenRichpedia 多模态知识图谱。它同时包含文本实体和视觉实体，所以除了普通的城市—景点关系，还能展示人物或地点与图片之间的关系。我没有直接复制原项目，而是抽取其中适合本次课程实验的数据，先用 Python 做格式解析、ID 统一和去重，再转换成统一节点表和关系表，最后导入 Neo4j，用 Cypher 查询和图视图完成可视化。

## 5.3 老师可能问：为什么不用 MySQL？

回答重点：

> MySQL 当然也可以存储实体表和关系表，但查询多跳关系时需要多次 JOIN；Neo4j 直接把实体建成节点、关系建成边，知识图谱的结构与数据库模型是一致的，所以本作业使用 Neo4j 更直观。

## 5.4 老师可能问：为什么需要预处理？

> 原始仓库的数据格式并不完全统一，例如 ID 有 `Q956` 和 `wd:Q956` 两种表示，图片映射有 `h/t` 和 `head/tail` 两种字段，而且部分文件是 JavaScript 对象而不是标准 CSV。因此如果不预处理，Neo4j 中会产生重复或难以匹配的实体。

## 5.5 老师可能问：`MERGE` 和 `CREATE` 有什么区别？

简洁回答：

> `CREATE` 每次都会创建新节点或新关系；`MERGE` 会先按照指定模式匹配，匹配不到时再创建。本项目配合唯一 ID 约束使用 `MERGE`，这样重复执行导入脚本不会不断产生重复实体。

## 5.6 老师可能问：知识图谱是什么？

可以从图结构回答：

$$
G=(V,E)
$$

其中 $V$ 是实体节点集合，$E$ 是实体间关系集合。与普通二维表相比，知识图谱强调“实体及实体之间的语义关系”。

## 5.7 展示顺序建议

演示时按这 4 个查询即可：

```cypher
MATCH (n) RETURN count(n);
```

```cypher
MATCH p=(c:City {name:'Beijing'})-[:HAS_SIGHT]->(s:Sight) RETURN p;
```

```cypher
MATCH p=(p:Person)-[:HAS_IMAGE]->(i:Image) RETURN p LIMIT 30;
```

```cypher
MATCH (n:Entity)-[r]-()
RETURN n.name, n.kind, count(r) AS degree
ORDER BY degree DESC LIMIT 10;
```

第一条证明数据确实导入，第二条最直观，第三条突出数据集特色，第四条体现你进行了简单图分析。
