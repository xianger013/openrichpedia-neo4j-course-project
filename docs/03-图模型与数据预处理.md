# 3. 图模型与数据预处理

## 3.1 为什么不能把原文件直接塞进 Neo4j

OpenRichpedia 仓库中的课程子集混合了多种 JavaScript/JSON 风格：

- `city.js` 是带尾随逗号的 JSON 风格层级数组；
- `city_sight.js` 使用 `const ... = [...]`；
- `pic_city.js` 使用短字段 `h/t`；
- `pic_people.js` 使用 `head/tail`；
- 地点 ID 同时存在 `Q956` 与 `wd:Q956` 两种写法；
- 图片 ID 又存在 `Q956_0`、`rp:032000` 和完整 URI 等形式。

因此首先要建立统一数据模型。

## 3.2 节点模型

统一节点 CSV：

```text
id,name,kind,source_file
```

节点类型：

| kind | 含义 |
|---|---|
| `City` | 城市 |
| `Sight` | 城市层级中的景点 |
| `Place` | 具有 Wikidata QID 的一般地点实体 |
| `Person` | 人物 |
| `Image` | 图片/视觉资源实体 |

Neo4j 中所有节点都带 `:Entity` 标签，再额外带一种具体类型标签，例如：

```cypher
(:Entity:City {id:'wd:Q956', name:'Beijing'})
```

## 3.3 关系模型

统一关系 CSV：

```text
source_id,target_id,type,source_file
```

关系类型只有三种：

```text
HAS_SIGHT
HAS_IMAGE
CONTAINS
```

这种白名单设计可以让导入代码简单、可审查，也避免动态 Cypher 类型被任意字符串污染。

## 3.4 ID 规范化

### Wikidata QID

若原始 ID 为：

```text
Q956
```

统一成：

```text
wd:Q956
```

若本身已经是 `wd:Q956`，保持不变。

### 城市图片 ID

`pic_city.js` 中图片 ID 例如：

```text
Q956_0
```

为了避免和普通实体 ID 混淆，转换为：

```text
img-city:Q956_0
```

### 人物和人物图片

`rpp:*` 与 `rp:*` 已具有命名空间，保留原值。

### 完整图片 URI

`contain.js` 的完整 URI 保留为节点主键，最后一个路径片段作为显示名称。

## 3.5 重复实体合并

同一个 ID 可能在不同源文件出现。采用类型优先级：

```text
City > Sight > Person > Place > Image
```

例如 `wd:Q956` 既可能由 `city_sight.js` 读成一般 `Place`，又可能由 `city.js` 确认是 `City`，最终保留 `City`。

## 3.6 关系去重

一条关系用三元组唯一标识：

$$
e=(source\_id,type,target\_id)
$$

只有三者完全相同才视为重复。

## 3.7 数据质量验证

预处理后至少检查：

1. 节点 ID 唯一；
2. 所有关系起点存在；
3. 所有关系终点存在；
4. 节点类型属于白名单；
5. 关系类型属于白名单。

若用邻接关系表示节点 $v$ 的度，可写为：

$$
d(v)=|\{e\in E\mid v\in e\}|$$

后续可以利用节点度寻找连接最丰富的实体。

## 3.8 处理代码在哪里

- 解析：`src/openrichpedia_kg/parsers.py`
- 建图/合并：`src/openrichpedia_kg/graph.py`
- CSV 输出：`src/openrichpedia_kg/io.py`
- 主入口：`scripts/preprocess.py`
- 独立验证：`scripts/validate_processed.py`

代码通过 `tests/` 中的小型固定数据执行自动化测试，因此不是“手工处理一次就结束”的不可复现实验。
